# 《此间》项目完整需求汇总｜供团队与 Agent 共享


文档性质：用户需求与已知情况汇总，不是已批准的实施方案，也不是已完成功能清单。  
适用对象：三人团队成员、Claude、Codex，以及后续协助策划、开发、美术和交付的 Agent。

> **最新且重要的补充：我们是一个三人零基础团队。** 后续方案必须让零基础成员能够实际照着执行，同时继续以作品效果、审美和可体验性为主要目标。
>
> 本文可以单独分享，不要求接收方读过此前对话。标为“已明确”的内容来自用户表述；标为“候选”“待确定”或“此前建议”的内容不能被擅自当成最终决定。文中的操作指导要求，是针对“零基础、需要可执行规划”的整理，不代表团队已经掌握相关技能。

## 1. 一分钟了解项目

我们希望做一款**高审美、可交互、有真实地点和文化依据的沉浸式文化旅行产品**。玩家进入一个美丽、可信的地方，在从早到晚的一天里自由探索、与人物交流、选择并完成不同主线任务，通过自己的选择形成独有的旅行回忆。

最初的想法是：“专门找一个好看的城市，在城市里面体验，就像真正去旅行了一样。”现在希望把它发展成可以实际操作、探索和参与的互动作品。

两个首要体验目标，按用户给出的顺序为：

1. 身临其境地探索与发现。
2. 认识当地文化与生活。

放松、景观欣赏、故事经历可以是体验结果，但不能挤掉这两个主目标。

| 项目 | 当前信息 |
|---|---|
| 团队 | 3 人，零基础 |
| 设备 | 3 台电脑；具体配置未知 |
| 制作周期 | 总共 2 天；成员可投入时间较多，具体每日时数未明确 |
| 已有进展 | 一名队员已用 Claude 跑通最小可行模型；其他制作尚未展开 |
| 原型信息 | 当前沟通者不知道工程路径、技术栈、仓库或预览链接；原型还未交给本次规划核验 |
| 制作方式 | 以 AI 辅助开发／vibe coding 为主，使用 Claude 和 Codex，可结合 Blender、图像生成等工具 |
| 主要设备方向 | 电脑端；后续考虑手机端 |
| 交付形式 | 必须可实际体验；主办方允许独立网页或其他互动作品 |
| 展示目标 | 评委和观众能快速进入、试玩、理解亮点，并愿意投票和分享 |
| 成本态度 | 优先考虑效果，token 消耗不是主要约束；新增资源由团队考虑后决定 |

## 2. 项目背景、命名与投票条件

### 2.1 参赛方向

- 用户已选择活动的**第二个方向：互动作品方向**，此前讨论中与“造世界”相关。
- 用户随后明确确认：**主办方允许独立网页或其他互动作品。** 因而不能把“必须在造世界中制作和交付”作为约束。
- 活动原始参考链接：[飞书活动资料](https://tcnr0pxctqhc.feishu.cn/wiki/HU1LwHKx8iA2GMk1qFbcFpgUnTe?from=from_copylink)。链接供追溯；本汇总不补写尚未确认的规则。

### 2.2 命名与气质

- 用户希望从项目内容本身出发，体现**高雅、文艺、高审美**，不是只围绕“三个人”命名。
- 前序讨论和规划使用的项目工作名称为**《此间》**，团队暂用名为**「三径」**。
- 项目名和队伍名是两件事。名称可继续调整，不影响核心产品要求。

### 2.3 投票与展示

- 用户非常关心哪个方案更能做得出彩，以及最终投票表现。
- **投票具体方式仍不清楚。** 当前按用户指定的假设分析：**现场试玩后投票**。
- 不得擅自假定票数规则、评委与观众权重、是否同池评选、试玩设备数量或每人实际可玩多久。
- 设计需要兼顾“短时间内看见亮点”和“确实有互动与文化体验”，而不是仅提供概念图、视频或口头介绍。

## 3. 地点与文化世界要求

### 3.1 用户提出的候选

主题类型可以有：滨海、古城、现代城市。候选地点包括：

- 杭州。
- 东京。
- 巴黎。
- 西安。
- 其他合适地点也可提出，但需要解释与目标、工期和素材条件的关系。

**城市尚未最终确定。** 用户希望 Agent 提供分析、比较并协助选择。

### 3.2 用户提到的画面灵感

- 夜晚灯火璀璨的大唐不夜城。
- 用户原描述为“东京富士山下樱花飘落”的景象。
- 日落时分的巴黎埃菲尔铁塔。
- 风车与牧场。

这些是审美与体验灵感，**不等于要求首版全部制作**。具体地点、地理关系、季节与文化语境要进一步核验；不能把灵感描述直接作为准确地理事实，也不能把各地标志性元素拼在同一个地方。

### 3.3 地方真实性

- 世界应有真实地点和文化依据。
- 重视真实地貌、建筑细节和地方生活。
- 避免笼统的异域符号拼贴。
- 不同文化世界可以有自己的光线、色彩和声音，但操作与交互语言应统一。
- 允许何种程度的地图压缩、建筑简化与艺术加工，目前没有明确边界，需要在方案中说清楚。

### 3.4 多世界愿景与首版范围

用户的流程包含“选择文化世界”，也提出了不同国家的生活节点，因此存在多世界／多章节的产品设想。但**两天内究竟做几个可玩世界，尚未由团队拍板**。

接手 Agent 应保留这一愿景，同时明确区分：

1. 产品最终希望具备什么。
2. 两天版本实际准备交付什么。
3. 哪些内容只作为后续计划展示。

不能把缩减范围的建议写成用户已经同意，也不能把未制作的入口展示成可玩内容。

## 4. 视觉、声音与整体审美

用户已经明确的美术方向是：**写实、经过审美化处理的电影感画面**。

- 真实地貌与建筑细节优先。
- 景色本身要有吸引力，能让人愿意进入、停留和拍照。
- 各主题在光线、色彩、环境声音上具有自己的气质。
- 统一交互方式，避免换一个世界就像换了一套产品。
- 高雅文艺不能只存在于标题、文案和宣传图中，应体现在实际可玩的画面和体验里。

尚未确定：具体美术参考、季节、画面品质标准、素材来源、角色风格、音乐方案、第一人称或第三人称视角，以及哪些景观最值得投入制作时间。

用户允许寻找真正高质量的开源项目，也允许使用 Blender、图像生成模型等工具。**这表示可以借助这些工具，不表示团队已经会用，也不表示某个开源项目或城市素材已经选定、验证或可直接交付。**

## 5. 玩家完整体验流程

用户明确提出的流程如下：

```text
选择文化世界
    ↓
抵达并认识今日目标
    ↓
自由观察第一个场景
    ↓
选择一条主线
    ↓
午后完成轻量文化任务
    ↓
傍晚做出影响后续的选择
    ↓
夜晚生成个人回忆卡
```

体验应包括：

- 从早到晚的一天。
- 自由探索，而不是全程被动观看。
- 与人物交流。
- 不同主线任务与选择。
- 选择对后续体验产生影响。
- 最终形成带有个人经历差异的旅行回忆。

用户尚未确定主线的具体数量、任务细节、人物数量、对话机制、结局数量或选择影响到什么程度。不要自行把具体数字补成已确认要求。

## 6. 场景、路线与生活支线

用户提出的空间组织为：

> 一个具体地点中的一条可理解的主要路线，包含 3 个精做且相互连接的场景：抵达点、文化活动点、收束点。

| 场景位置 | 需要承担的作用 |
|---|---|
| 抵达点 | 进入地方、认识目标、开始观察和探索 |
| 文化活动点 | 接触当地生活、人物或文化任务 |
| 收束点 | 承接后续选择，并形成一天的结束与回忆 |

用户还提出“穿插三个分线”，举例为：

- 中国酒楼。
- 东京酒吧。
- 法国咖啡厅。

这些节点需要与对应的地点／文化世界配套。当前表述仍有待澄清之处：是全部产品共三个生活分线，还是每个世界三个分线，以及两天版本是否要全部实现，**尚未明确**。

时间变化应通过**光线、声音和剧情**表达。用户没有要求真实等待一天，也没有指定一定采用连续昼夜模拟。

## 7. 功能需求与未定细节

### 7.1 自由行走与探索

- 用户明确提出“自由行走”。
- 玩家应能主动观察环境、发现内容并选择行动。
- 具体移动操作、可走范围、镜头视角和导航方式待选型。
- 点击热点、切换全景等方案如果不能提供所期待的自由行走，需要明确解释体验差异，由团队决定是否接受，不能直接当作等价实现。

### 7.2 拍照与打卡——重点设计项

- 用户特别强调拍照、打卡的重要性。
- 希望寻找适合的地标，并优化设计为拍照点。
- 拍照应融入旅行过程与个人回忆。
- 具体取景操作、推荐机位、照片保存、回忆卡如何使用照片、是否有滤镜或构图引导，都需要后续方案确定。
- 不能把“有几张漂亮宣传图”当成已经满足玩家拍照需求。

### 7.3 天气

- 用户明确希望有天气。
- 天气种类、变化方式、是否由玩家选择、是否影响任务和拍照，尚未确定。
- “晴／雨两套”是前版建议，不是用户指定的最终数量。

### 7.4 人物交流与文化任务

- 玩家需要能与人物交流。
- 任务应轻量，并服务于探索地方和理解文化生活。
- 没有要求必须使用实时大模型对话；固定对白、分支对白或其他实现方式都应先比较效果与可行性。
- 不应把文化体验自动简化为大量阅读或知识考试；具体玩法仍由方案提出。

### 7.5 选择与回忆

- 傍晚要有一个影响后续的选择。
- 夜晚生成个人回忆卡。
- 旅行选择应让不同玩家的回忆具有差异。
- 具体差异体现在哪里、卡片内容与格式、是否下载或在线分享，尚需设计。

### 7.6 节奏与续玩

- 现场快速试玩：目标 **2—3 分钟**。
- 完整章节：目标 **10—20 分钟**。
- 允许跳过旁白。
- 支持在节点续玩。
- 快速试玩如何与完整章节共用内容、进度如何保存、是否需要账户等，目前没有定案。

上述时长是目标，不是已经测得的结果；不能通过强制等待或拖长旁白来冒充完整内容时长。

## 8. 三人零基础团队的实际条件

### 8.1 已知条件

- 三名成员，三台电脑。
- 最新补充：团队零基础。
- 总制作周期两天，可用时间较多。
- 用户倾向以最终效果为主，不希望仅因为当前技能情况就直接排除有表现力的方案。

“零基础”和“效果优先”需要一起处理：**由 Agent 承担更多技术分析、实现和排错，同时把人工操作拆清楚；不能假定团队会编程、Git、3D 建模、命令行或部署，也不能承诺两天内毫无限制地实现完整愿景。**

### 8.2 后续指导应达到的可执行程度

以下是适配零基础团队的交接要求：

- 说明每一步由谁做、用什么工具、在哪里操作。
- 涉及命令时，说明在哪个目录执行、应看到什么结果。
- 涉及文件时，给出明确路径、文件名和修改内容。
- 涉及术语时，附一句普通话解释，不只抛出技术名称。
- 明确输入、输出、完成标准和下一步。
- 区分 Agent 可以直接完成的工作和必须由成员操作的工作。
- 提供关键步骤的检查方法，以及常见失败后的处理方式。
- 把工具安装、首次运行、账号／权限配置、三台电脑同步和学习操作的时间算进计划。
- 不因为成员不会判断错误，就反复要求他们执行未经核实的命令或重装整个环境。

### 8.3 分工状态

- 尚未确定成员的能力偏好、姓名与具体岗位映射。
- 用户希望先看团队是否有偏好；如果没有，可以参考此前分工建议。
- 用户希望 **AI 提供多个方案，并列出详细优缺点，交由队伍考量选择**。
- 后续计划应帮助三个人协作，而不是简单让三个人分别做三个完全独立、难以整合的作品。

## 9. 开发方式、已有进展与资源

### 9.1 AI 辅助制作

- 主要使用 Claude 和 Codex。
- 可调用 Blender、图像生成模型等其他工具。
- 可寻找高质量开源项目、现成素材和合适软件，提高最终效果。
- 用户更关心体验结果；token 消耗不作为主要考虑。
- 具体工具分工、技术栈和工程协作方式尚未确定。

### 9.2 已有最小可行模型

用户原表述为“已经用 Claude 跑了最小可行模型，其他还没做”。之后补充：不是当前沟通者本人跑的，不清楚具体情况。

因此，目前只能确认：**据团队反馈，已有一名队员用 Claude 跑通过一个最小模型。**

以下均未知：

- 工程在什么路径，是否有仓库或可访问预览。
- 使用何种技术，如 Three.js、React、Unity 或其他。
- 已经实现了哪些可用功能。
- 其他电脑能否复现运行。
- 是否有可继续使用的场景、美术资产和部署。

接手 Agent 应先向原型制作者取得实际项目并核验。不能写成“已验证能自由行走／拍照／部署”，也不能在没看工程前认定它必须保留或必须推倒重做。

### 9.3 预算与硬件

- 三台电脑的配置未知。
- 具体资源预算尚未给出。
- 如需要付费模型、素材、软件、服务器或其他资源，应提出用途与选项，由队伍考虑后决定。
- “以效果为主”不等于无限预算，也不代表已经授权任何购买。

## 10. 交付、访问与传播

### 10.1 核心交付标准

用户给出的标准是：

> 一个可实际体验的互动作品。作品形态不限，可以是游戏、互动叙事、解谜体验、沉浸式故事、互动影像，或其他能够让用户参与其中的创意形式。

允许形态灵活，但仍需体现本项目的文化旅行目标与用户参与。

### 10.2 设备和访问

- 主要面向电脑。
- 需要考虑评委如何快速打开与使用。
- 后期可考虑手机端，但用户没有要求首版必须达到手机端完整可玩。
- 需要考虑活动后其他人如何继续体验。
- 独立网页是一种允许的形式，**还不是已最终确认的技术或交付方案**。

### 10.3 分享与扩散

- 用户明确要求考虑如何扩散和分享。
- 个人回忆卡可以与分享设计结合，但具体机制待定。
- 分享链接、图片下载、扫码访问、在线回忆页等可以提出比较，不能当作均已确认必做。
- 需要区分“把作品入口分享给别人”与“把某位玩家的个人照片／回忆分享给别人”。

目前没有确认账号系统、多人联机、支付、社交广场、排行榜或云端相册需求；不要自行加入首版范围。

## 11. 用户希望 Agent 提供什么

用户已要求一份详细项目规划，供成员和 Agent 共同阅读与执行，至少覆盖：

1. 对项目理解、可行性与主要风险的分析。
2. 候选城市／地点的比较与选择建议。
3. 如何实现高审美与沉浸体验，而不只堆功能。
4. 具体做哪些场景、任务、交互和回忆内容。
5. 多种制作／协作方案及详细优缺点，方便团队选择。
6. 三个人如何分工，如何整合。
7. 两天内的具体排期、任务清单和工作流。
8. Claude、Codex 和其他工具如何配合。
9. 合适的开源项目、素材与资源建议，并区分已验证和未验证的内容。
10. 现场快速试玩、完整体验、交付与传播安排。
11. 完成标准、验证办法、做不完时的取舍。
12. 适合零基础成员照着执行的具体步骤。

**当前这份文件的任务只是汇总需求。** 后续 Agent 可以据此重新评估、修改或细化方案；不要把此前某个建议当作用户已批准的唯一实施路线。
